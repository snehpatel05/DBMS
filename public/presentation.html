01. Operational Domain

Problem Statement & Operational Scope

🚨 Paper Registry Challenges
  • • Misplaced Case Files: Traditional district court registries risk physical damage or lost plaints.
  • • Appearance Latency: High operational friction finding next hearing dates, summons status, and interim applications.
  • • Lack of Auditability: Absence of cryptographic, immutable audit logs for procedural changes.
Core Bottleneck: Fragmented institutional memory without atomic database enforcement.
🎯 System Scope & Boundaries
  • • Single Court Registry: Engineered specifically for a district Sessions Division registry handling heavy daily dockets.
  • • Autonomous Architecture: Fully self-contained without fragile real-time external network dependencies.
  • • 6-Stage Lifecycle: Filing → Registration → Scrutiny → Cause List → Court Proceedings → Final Disposal.
In Scope: 100% of internal relational judicial workflows.
👥 Role-Based Authorization
  • • Judge (Bench): Presides trials, enters private notes, signs binding decrees, disposes cases.
  • • Advocate (Bar): Manages retainer portfolio, files pleadings, signs digital Vakalatnamas.
  • • Clerk (Registry): High-volume plaint intake, summons issuance, daily cause list generation.
  • • Litigant (Citizen): Read-only docket tracking, hearing alerts, lawyer appointment consent.
  • • Administrator: Schema audit, trigger verification, account management.
Enforcement: Cryptographic tokens & DB-level projection masking.

05. Logical Design

Logical Relational Schema & Referential Integrity

📋 18 Normalized Relations (R1 to R18)
User ISA Subtypes: R1 SYSTEM_USER, R2 ADVOCATE, R3 LITIGANT, R4 JUDGE, R5 CLERK, R6 COURT_ADMINISTRATOR
Case Registry & Parties: R7 CASE (CNR PK), R8 CASE_PARTY (CNR, Litigant_ID), R9 CASE_ADVOCATE (CNR, Advocate_ID)
Scheduling & Summons: R10 CAUSE_LIST, R11 HEARING, R12 WITNESS, R13 SUMMONS
Decrees & Pleadings: R14 ORDER, R15 DOCUMENT, R16 VAKALATNAMA
Alert Notifications: R17 ALERT, R18 ALERT_RECIPIENT
Domain Integrity: CHECK constraints strictly enforce valid statuses, urgency grades, and user roles.
🔒 29 Foreign Keys: Why ON DELETE RESTRICT?
Statutory Judicial Non-Repudiation:
In legal administration, court dockets, evidence, and orders must never be silently erased via cascade. Deleting a parent case with child proceedings is physically rejected by the DB engine (PostgreSQL Error 23503).
  • • ON UPDATE CASCADE: Guarantees key updates (e.g., CNR or User_ID) propagate seamlessly to all child tables.
  • • Recursive Integrity: CASE_ADVOCATE.(CNR, Assigned_By) references CASE_ADVOCATE.(CNR, Advocate_ID).
Result: Absolute zero orphan records or unverified deletions across the entire database.
06. Normalization Proof

Rigorous Step-by-Step Normalization to BCNF

1️⃣ 1NF & 2NF Verification
  • • 1NF: All column domains are atomic. Zero multi-valued or repeating attributes. Primary key established on every table.
  • • 2NF: Evaluated all 7 composite-key relations (R8, R9, R11, R13, R14, R15, R18).
  • • No Partial Dependencies: Every non-prime attribute depends on the entire candidate key, never a proper subset.
2️⃣ 3NF Redundancy Resolution

Two Transitive Violations Discovered & Fixed:

R11 HEARING: (CNR, Seq) → CauseList_ID → Hearing_Date.
Anomaly: Clerk could insert a conflicting date.
Fix: Dropped Hearing_Date; read from CAUSE_LIST.List_Date.
R14 ORDER: (CNR, Seq) → Published_Date → Publish_Status.
Fix: Dropped derivable status; evaluated dynamically via Published_Date IS NOT NULL.
3️⃣ Strict BCNF Compliance
  • • Determinant Rule: In every non-trivial functional dependency \(X \to Y\), \(X\) is a superkey.
  • • No Overlapping Keys: Tested all relations with multiple candidate keys (R1, R2, R7, R10, R16).
  • • Lossless Decomposition: All table joins use key attributes.
  • • Dependency Preservation: 100% of functional dependencies preserved.
07. Database Hardening

PL/pgSQL Triggers & Judicial Integrity Enforcement

🔒 Irreversible Case Disposal (fn_check_disposal)

Enforces the legal lifecycle transition from Pending to Disposed:

  • • Final Judgment Guard: Rejects setting status to 'Disposed' unless an official published Final Judgment order exists in R14.
  • • Permanent Seal: Once marked Disposed, the case is sealed against any further edits or deletion.
IF NEW.case_status = 'Disposed' THEN SELECT COUNT(*) INTO v_order_count FROM court_order WHERE cnr = NEW.cnr AND order_type = 'Final Judgment' AND published_date IS NOT NULL; IF v_order_count = 0 THEN RAISE EXCEPTION 'Disposal requires published Final Judgment.'; END IF; END IF;
⚖️ Lead Counsel Hierarchy (fn_check_assigner_is_lead)

Protects attorney representation protocol:

  • • Enforces that only an attorney registered as 'Lead' on that case can assign junior associate counsel.
  • • Blocks unauthorized advocate impersonation at the SQL trigger layer.
SELECT case_role INTO v_assigner_role FROM case_advocate WHERE cnr = NEW.cnr AND advocate_id = NEW.assigned_by; IF v_assigner_role != 'Lead' THEN RAISE EXCEPTION 'Only Lead Counsel can assign associate advocates.'; END IF;
👁️ Bench Note Confidentiality (SQL Projections)
  • • Judicial bench notes (R11) contain private trial impressions.
  • • Zero Leakage: Masked via SQL CASE WHEN role = 'Judge' AND judge_id = req.user.id THEN bench_note ELSE NULL END.
  • • Non-judges receive NULL directly from the database engine.
📝 Live Trigger Audit Trail (fn_audit)
  • • Automatically logs every INSERT, UPDATE, and DELETE.
  • • Records table name, operation type, record key, and timestamp into audit_log.
  • • Fully accessible to Court Administrators on the live dashboard.
08. Algorithmic Scheduling

Statutory Cause List Generation Algorithm (REQ-05)

📜 Multi-Criteria Deterministic Priority Rules
1. Statutory Urgency Tier (Primary Filter)

Statutory Urgency matters are scheduled first, followed by Urgent, then Normal plaints.

2. Witness Summons Attendance (Secondary Filter)

Cases with summoned witnesses physically appearing in court take priority to prevent witness travel wastage.

3. Case Filing Age Tiebreaker

Earliest filing dates break ties within the same priority tier. Guarantees older matters are never starved by new filings.

Judicial Load Balancing: Rotational round-robin assignment distributes dockets equally among sitting judges.
⚡ Single Transactional SQL Implementation
SELECT c.cnr, c.case_number, c.statutory_urgency, c.filing_date, COUNT(s.summons_date) AS witness_count FROM court_case c LEFT JOIN hearing h ON h.cnr = c.cnr LEFT JOIN summons s ON s.cnr = h.cnr AND s.hearing_seq_no = h.hearing_seq_no WHERE c.case_status = 'Pending' GROUP BY c.cnr ORDER BY CASE c.statutory_urgency WHEN 'Statutory Urgency' THEN 1 WHEN 'Urgent' THEN 2 ELSE 3 END ASC, COALESCE(COUNT(s.summons_date), 0) DESC, c.filing_date ASC LIMIT 25;
Executed inside an atomic transaction: creates the cause list header (R10) and links hearings (R11) instantaneously.

11. Viva Voce Preparation

Anticipated TA Viva Questions & Defenses

Q1: "Why did you normalize to BCNF instead of stopping at 3NF?"

Defense: In 3NF, transitive dependencies in HEARING (hearing date depending on cause list) and ORDER (publish status depending on publish date) allowed update anomalies. Decomposing them to BCNF eliminates all redundancy losslessly while preserving every dependency.

Q2: "Why use ON DELETE RESTRICT instead of ON DELETE CASCADE?"

Defense: Legal records demand statutory non-repudiation. In a real judiciary, deleting a case must never silently wipe active hearings, decrees, or summons. RESTRICT guarantees no legal document vanishes accidentally.

Q3: "How do you guarantee bench note privacy if someone calls the API directly?"

Defense: Bench note confidentiality is enforced directly in the SQL projection query via CASE WHEN role = 'Judge' AND judge_id = req.user.id THEN bench_note ELSE NULL END. Non-judges receive NULL from the database engine itself.

Q4: "How does the cause list algorithm prevent starvation of older cases?"

Defense: After prioritizing statutory urgency and witness attendance, the algorithm uses filing_date ASC as the deterministic tiebreaker, guaranteeing long-pending plaints are scheduled before newer filings.
